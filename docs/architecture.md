# Architecture decisions

## Desktop shell and toolchain

Tauri 2 uses native window chrome and each platform's webview. React + custom CSS controls the calendar visuals; Radix supplies editor/dialog focus behavior. System fonts require no network downloads. Node 24 LTS is the CI baseline; pnpm 12.10.1 and Rust 1.99.0 are pinned. Dependency resolutions are recorded in the pnpm/Cargo lockfiles. The current host has Node 26.8.2; record checks accordingly rather than claiming local Node 24 execution.

The shell exposes only `get_app_info` in phase 0. No filesystem, arbitrary shell, network, or credential commands are exposed to the renderer. CSP allows local assets and IPC; inline styles are necessary for calendar positioning. Native controls keep platform close/minimize/maximize behavior. Production packaging has an application icon derived from the repository SVG.

Canonicalize OS/webview locales before formatting: Linux can expose POSIX tags such as `en_US.UTF-8` or `C`, which Intl/Luxon reject directly. Convert valid regional tags to BCP 47 and fall back to Intl's system locale. Native startup checks caught this incompatibility; regression tests cover it. Below the requested minimum window width, collapse the sidebar and wrap the toolbar to accommodate tiling compositors that override application minimum sizes.

## Boundaries

Current local data flow: React calendar → typed IPC client → Rust `CalendarService` → SQLite. Phase 4 adds registered provider dispatch between the service and persistence or remote adapters. Frontend views own rendering/selection/interaction state, never provider-specific event mapping, SQL, tokens, or authentication.

The browser design harness uses `PrototypeRepository` explicitly. It is in-memory and independently undoable; this is a design harness, not the permanent provider implementation. Native startup binds the typed IPC client and never loads the browser fixture repository. No sample events should seed a user's database.

Contracts originate in `src-tauri/core/src/contracts.rs`. `pnpm types:generate` uses ts-rs to export declarations to `src/generated`; CI rejects drift. Stable internal UUIDs differ from future remote IDs. Timed values cross IPC as UTC ISO strings with an IANA source zone; all-day values cross as ISO calendar dates, with exclusive end dates. Keep optional fields empty strings in the v0 contract.

## Persistence and undo, phase 2

Use bundled SQLite through rusqlite, at the OS application-data directory, behind a backend repository. Run blocking database work off the UI thread. Version migrations transactionally; never recreate/reset a database after migration or open failures. Add query indexes and select events overlapping the requested interval. Store preferences alongside local application data. Serialize mutations through the calendar service; undo is session-scoped and compensates successful mutations.

The backend validates titles, date ordering, valid time zones, and DST ambiguity. Nonexistent local times must be rejected; repeated local times require selecting an offset. Luxon supports renderer layout/formatting; Rust chrono/chrono-tz owns authoritative validation. Test shared time fixtures across boundaries. The phase-1 editor intentionally does not implement those backend guarantees yet.

## Provider extension, phase 4 and later

The provider registry exposes descriptor, capabilities, normalized calendar discovery, bounded event listing, and normalized create/update/delete operations. Authentication and sync are backend extension points. Unsupported capabilities produce typed errors. Contract tests exercise local and test-only adapters, independent calendar identities, and read-only behavior without changing views.

The first remote provider introduces a common cached adapter/sync coordinator, rather than copying caching into Google-specific code. Durable offline mutations use an outbox with retries and explicit conflicts. Subsequent Google/Microsoft/CalDAV implementations map their auth, IDs, cursors, revisions, event formats, and errors to that common layer. New recurrence/invitation features need a separate domain/UI increment.

The credential service stays behind the backend boundary. Use persistent OS stores (Keychain, Windows Credential Store, Linux Secret Service), namespace entries by application/account, and never return credentials to the renderer. Locked/unavailable stores block connected accounts. Data at rest is not application-encrypted in v0. No session-only or plaintext fallback.

## Verification and distribution

Vitest covers layout and prototype repository behavior; Playwright covers renderer flows and captures review images. Browser checks are not evidence of native integration. Phase 4 adds WebdriverIO embedded Tauri automation on Windows/macOS/Linux, with plugins enabled only in test builds, plus real-platform checks.

The active CI desktop target is Linux on Ubuntu 24.04; Windows/macOS entries remain commented out per the latest user decision. The repository is now rooted at `project-cal`, so workflow paths match the app layout. Origin is `EPMatt/aika`, with `main` as the publication branch. Hosted CI and cross-platform execution still require observing actual workflow results. See `docs/repository-history.md` for the relocation and rewritten revision mapping. Windows/macOS launch checks remain external verification tasks.

Private distribution uses Windows installers, per-architecture macOS DMGs with ad-hoc signing, and Linux AppImage/deb/RPM. There is no public signing, notarization, updater, analytics, or server in v0.

## Phase 2 implementation

`CalendarService` owns the SQLite connection and session compensation stack. Tauri lazily opens `calendar.sqlite3` in `app_data_dir` from a blocking worker, including directory creation and transactional migration. A shared mutex serializes access; renderer mutations also queue in invocation order. Initialization failures are returned as typed errors and may be retried; no reset fallback exists. Schema version 1 stores the default calendar, normalized event payloads with indexed range columns, and validated preferences. Future schema versions are rejected. Browser fixture URL parameters are ignored in native startup.

IPC commands are `calendar_snapshot`, `save_event` (explicit create/update intent), `delete_event`, `undo_event`, `get_preferences`, `set_preferences`, and `resolve_local_time`. Snapshot queries use exclusive instant/date bounds and include overlapping events. Event IDs are UUIDs; the default calendar retains the contract identity `local-default`. UTC instants are canonicalized before persistence. Errors carry code/message/offset choices without exposing database paths or SQL.

The editor submits raw local wall-clock values to Rust before building its UTC contract. Gaps are rejected and folds require explicit UTC-offset selection. A UTC instant already determines its offset unambiguously; `save_event` validates that normalized contract and the source IANA zone. Shared fixtures in `tests/fixtures/time.json` verify Rust and Luxon resolution. Failed save/delete input remains open. Undo compensates only committed mutations, remains available after failed writes, and clears on application restart. Preferences are durable and do not enter event undo history.

### Phase 2 decisions and rationale

- **Store normalized JSON alongside query columns.** Schema v1 keeps the full `CalendarEvent` as JSON and duplicates its calendar identity, kind, start, and end in SQL columns. The payload preserves the shared contract without reconstructing each field from SQL; the `(kind, start, end)` index supports overlap queries without parsing JSON. The service writes payload and query columns together in one statement. Future event-contract changes must account for existing payloads as well as SQL schema migrations, even when no column is added.
- **Query instants and calendar dates separately.** `EventRange` carries UTC start/end instants for timed events and start/end dates for all-day events. The renderer derives both from the visible interval in the device zone. The service validates ordering within each pair and selects `event.start < range.end && event.end > range.start`. This includes overnight and multi-day events while excluding touching boundaries; it avoids converting all-day dates into instants. Phase 2 trusts the client to keep the two pairs consistent and does not impose a maximum query span or pagination.
- **Use one connection and two levels of serialization.** A process-local mutex protects the connection, lazy initialization, preferences, and compensation history; database operations run on blocking workers. The renderer queues event and preference mutations together in invocation order, and a rejected operation does not stop subsequent queued work. Reads remain separate; snapshot request versions discard obsolete responses. SQLite foreign keys are enabled and lock contention waits up to five seconds. This establishes ordering within one running application; it provides no shared undo history or revision coordination across application processes.
- **Compensate individual events.** Each successful event mutation records its ID and previous event, or absence for creation, in a memory-only stack. Undo restores that event or removes the created event, then consumes the entry only after the compensating transaction commits. This avoids retaining whole-calendar snapshots and preserves unrelated events. The stack has no size cap, redo, durable journal, or cross-process conflict check in phase 2. Preferences never enter it.
- **Keep creation intent separate from revision checks.** The renderer generates UUID event IDs. `save_event(existing)` rejects a create whose ID already exists and an update whose ID is missing; delete rejects a missing ID. These checks prevent accidental creation/replacement when editor intent no longer matches existence. They do not detect another edit to an existing event: there is no revision token, and a later successful update replaces its payload. Provider revisions and sync conflicts remain later work. Titles are trimmed and limited to 1–300 Unicode characters; source zones must be valid IANA zones, and persisted instants use UTC with millisecond precision.
- **Persist one complete preference record.** The singleton JSON record contains appearance, last view, and sidebar visibility, with defaults `system`, `month`, and `true`. Native startup loads it before enabling preference writes, preventing first-render defaults from overwriting saved values. Changes submit the full record through the mutation queue. Automatic sidebar collapse below 900 pixels also changes the persisted visibility; phase 2 has no separate preferred-versus-responsive sidebar state. Selected date and calendar visibility are not persisted. Preference failures have their own visible retry state so a successful event query cannot hide them.
- **Retain a fixed local-calendar identity until provider proof.** Migration v1 inserts `local-default` / Personal, and the service accepts events only for that identity. Snapshot provider ID, color, and writable capability are supplied by the service as fixed local metadata. Calendar discovery, configurable metadata, and read-only enforcement through provider capabilities are phase-4 extensions, rather than implemented registry behavior.

These decisions shipped in `1ce59e4`. They describe the phase-2 scope and its limits; phase-3 interaction decisions below build on the same persistence contracts.

## Phase 3 interaction boundary

Calendar gestures remain renderer interaction state. Month selection creates an all-day date range with an exclusive end; timed selections resolve raw snapped wall-clock fields through `resolve_local_time` before opening the editor. Native gaps/folds therefore cannot be silently normalized by Luxon. Timed drops retain elapsed duration; resizing changes only the end instant and rejects end-before-start. Event types change in the editor. Saves use the existing explicit-update IPC and session undo path; failed gestures never optimistically replace displayed events. Users retry gestures or select offsets in the editor.

All-day bars are clipped to each visible week and assigned nonoverlapping lanes using exclusive date bounds. Month capacity reserves those lanes and exposes hidden events through the existing overflow popover. Week/day rows grow to fit their lanes. Pointer capture supports selection/resizing, Escape cancels selection, and timed selections scroll near the viewport edge. Focusable date cells, all-day rows, time columns, event buttons, and date/time editor inputs provide keyboard alternatives. The live clock refreshes every 30 seconds, including the native current date at midnight.

### Phase 3 decisions and rationale

- **Reuse normalized CRUD contracts.** Creation opens an unsaved editor draft; moving and resizing submit a complete normalized event through `save_event` with explicit update intent. Gestures add no IPC commands, generated contract fields, SQLite migrations, or separate undo stack. This keeps mouse and keyboard editing on the same validation/persistence path and leaves future provider dispatch behind the service boundary.
- **Confirm writes before refreshing displayed data.** Gesture previews are temporary renderer state. Native saves must succeed before requesting a fresh bounded snapshot; request versions discard stale snapshot responses. Failed writes leave the displayed event and backend compensation history intact. The browser harness refreshes its in-memory repository instead. This avoids inventing rollback behavior in the renderer.
- **Resolve wall time before constructing instants.** Pixel positions become local date/time strings snapped to 15 minutes, then pass through `resolve_local_time`. Rust remains authoritative in native execution; Luxon resolution is confined to the browser harness. Gaps and folds reject the gesture, and the editor supplies explicit offset selection. A timed move preserves elapsed duration across DST changes; resizing resolves the new end independently. Date drops preserve the local clock time; event type changes remain explicit editor actions.
- **Keep span layout derived from dates.** `layoutAllDaySpans` computes clipped columns and collision lanes from normalized exclusive date ranges. Those columns/lanes are never persisted or sent over IPC. Month overflow includes hidden all-day events without rendering them again as repeated chips. Week/day rows grow with lane count. This lets providers supply ordinary normalized events without knowing the renderer's grid or density.
- **Use existing browser input mechanisms.** Pointer capture handles range selection and end resizing; native HTML drag-and-drop transfers event IDs for moves. Keyboard users edit the same date/time fields through the anchored editor. Timed selection stays within one column and resizing supplies an end handle; overnight creation and start changes use the editor. Native webview input behavior still requires the phase-4 platform checks.

These decisions were implemented in `433172a`. Service tests prove SQLite behavior; browser and mocked-IPC tests prove renderer behavior; the Linux smoke check proves mounting and IPC startup. None substitutes for embedded native gesture/CRUD automation or other-platform verification.

## Phase 4 provider and quality decisions

- **Register adapters behind the unchanged IPC service.** `CalendarService` now delegates event operations to `ProviderRegistry`, which registers a SQLite-backed `LocalProvider` in production. The backend-only `Provider` trait defines descriptors, calendar discovery, bounded snapshots, normalized CRUD, and optional undo/authentication/synchronization. Authentication/sync remain unsupported extension points: no accounts or remote traffic are enabled. Application preferences stay on the registered local adapter. There is no renderer API for registration or credentials.
- **Discover identities atomically.** Registration rejects duplicate provider IDs, globally duplicated calendar IDs, and calendars claiming another provider. Discovery metadata is frozen for the registry session; snapshots use that metadata and reject events or snapshot identities belonging to another calendar. Later account/discovery changes need explicit registry refresh and invalidation, rather than mutating a renderer fixture. Each adapter must scope existence checks, updates, and deletion to the requested calendar. SQLite queries now filter the local calendar; conflicting event IDs in another persisted calendar cannot be overwritten or deleted.
- **Enforce capabilities at dispatch.** Both provider and calendar writability must permit a mutation. Read-only create/update/delete/undo fail before entering an adapter. Shared validation trims titles, validates UUIDs and times, and canonicalizes timed instants before adapter calls. Snapshots require ordered instant/date bounds and limit calendar-date ranges to 366 days (367 elapsed days allow DST/zone boundary differences). The registry does not add pagination or synchronize revisions; those remain remote-integration work.
- **Prove the boundary with an independent test adapter.** An in-memory second adapter supplies distinct writable/read-only calendars under `cfg(test)` only. Shared tests run normalized CRUD on SQLite and the test adapter, exercise cross-calendar deletion and update intent, reject duplicate discovery, and reject deliberately leaked snapshot data. Local compensation undo remains unchanged; the test adapter returns `unsupported` for undo. Production cannot register sample/test providers through a feature or IPC command.
- **Use persistent native credential stores without fallback.** `CredentialService` wraps keyring 3 with Apple-native Keychain, Windows-native Credential Manager, and Linux synchronous Secret Service support. Linux kernel/session keyrings are not enabled. Entries use application namespace `dev.projectcal.desktop` and a length-prefixed provider/account identity to prevent delimiter collisions. Only a genuine missing entry becomes `None`; all other native failures become a redacted `credentialUnavailable` error. Deletion of a missing entry is idempotent. Secrets are returned only to backend callers; no secret command, renderer storage, SQLite field, or raw native-error logging was added. Dependency injection is internal to tests. A disposable real-store roundtrip verifies Linux access separately from simulated failures.
- **Render from normalized metadata and capabilities.** The same calendar views and editor now consume snapshot calendar identity/name/writability. New drafts use that identity, creation waits for discovery, read-only events remain inspectable, mutation controls and drag/resize affordances are disabled, and keyboard creation respects the capability. No view branches on a provider name. This is capability proof for one visible calendar, not a multiple-calendar product feature. The prototype's default local metadata remains its explicit design-harness default.
- **Correct ARIA structure while retaining layout.** Month all-day spans are grid cells with column/span metadata; unlabelled layout containers no longer claim inaccessible labels. Calendar surfaces are labelled regions and the view switcher is a labelled group. Axe audits cover all three views, the editor, and Settings in both themes with reduced motion. Automated audits complement keyboard tests; they do not certify Narrator/VoiceOver/Orca behavior.
- **Keep native automation out of production.** WebdriverIO connects directly to `tauri-plugin-wdio-webdriver` 1.5's embedded loopback server. Only the optional `native-test` Cargo feature links/registers it; release compilation explicitly rejects that feature. Ordinary debug builds also omit the driver. The test build requires `AIKA_TEST_DATA_DIR`, and the runner creates/deletes a disposable database directory across application restarts. No production capability grants or frontend mocking plugin were added. Direct W3C client use avoids the extra execute/mocking bridge required by `@wdio/tauri-service`. Driver clicks are dispatched with focus before click because its built-in post-click focus dismisses Radix virtual-anchor popovers. Some driver input is synthesized inside the actual webview, so trusted OS drag/resize and assistive-technology checks remain a separate manual matrix in `docs/quality.md`. The [embedded driver documentation](https://webdriver.io/docs/desktop-testing/tauri/plugin-setup) documents support for the three desktop webviews; execution on Windows/macOS remains pending.
- **Choose a Linux rendering compatibility default based on native evidence.** On this Arch/Wayland host the default WebKitGTK DMA-BUF path left the editor fade at opacity zero and produced stale captures. `WEBKIT_DISABLE_DMABUF_RENDERER=1` allowed the complete native suite to pass. Linux startup sets this default before GTK/WebKit/threads start, preserving any explicit environment value. It trades accelerated buffer transport for reliable calendar rendering; other hardware still needs the manual platform checks. This uses [Tauri's documented Linux graphics workaround](https://v2.tauri.app/develop/debug/linux-graphics/); it changes neither the user's desktop configuration nor their system environment.

No schema or generated IPC contract changed in phase 4. Existing SQLite data, preferences, session undo, and source-zone behavior retain their contracts. Native integration results, renderer results, OS-store results, and unexecuted platform/manual checks are recorded separately in the phase-4 handoff.

## Repository structure decision

At the user's request after phase 4, Git metadata lives physically in `project-cal/.git`, and all retained commit trees place the app files directly at the repository root. The branch is `main`; origin retains its existing URL. Filtering only the original app subtree preserves the complete app history while keeping neighboring projects outside the repository. Every rewritten tree was compared with its original subtree before moving metadata. Original metadata/bundle recovery copies remain in `/tmp`, and the pre-existing uncommitted `.gitignore` change remains local. `docs/repository-history.md` maps earlier handoff revisions. This resolves the previous workflow-root mismatch without changing packaging or silently enabling disabled platform jobs.

## Phase 5 private distribution boundary

`pnpm alpha:build` maps four explicit target triples to Linux deb/RPM/AppImage, Windows current-user NSIS, and separate Intel/Apple Silicon macOS DMGs. macOS remains ad-hoc signed, with minimum version 14.0; Windows/Linux candidates are unsigned. The command builds release mode without test features, removes only generated bundle output, rejects target-directory overrides and version drift, and refuses to overwrite an existing candidate. The existing Rust release guard prevents a test-driver feature from shipping.

RPM uses Tauri's built-in bundler and GTK 3/WebKitGTK 4.1 shared-library requirements. The Linux release CI baseline is pinned to Ubuntu 24.04 and runs `scripts/linux-rpm-check.py` before upload, checking candidate checksums, RPM metadata/dependencies, the x86_64 executable and permissions, launcher, and icons without installing the package. Fedora DNF installation and desktop/restart checks remain separate pending acceptance evidence. The standalone CLI is not included in desktop installers.

Collection requires exactly one installer per expected extension and excludes other generated files. Candidate names include version and architecture; the manifest records source revision (including dirty state), sizes, hashes, signing, and pending acceptance. SHA256SUMS also covers the manifest and release notes. Hashes establish byte integrity, not publisher authenticity. CI uploads this private candidate directory separately from debug automation evidence, retaining the user's disabled Windows/macOS jobs. No updater, publishing, signing service, credential access, or production data-directory override is introduced.

Installer execution and version upgrades require disposable OS accounts and actual production releases. Debug native CRUD/restart checks cannot establish install/update behavior. A first-alpha same-version replacement must be labelled separately from a true upgrade. See `docs/alpha/verification.md`; unexecuted platform/manual checks and the final user gate remain pending.

### Phase 5 decisions and rationale

- **Use one explicit release path for local builds and CI.** `scripts/alpha.mjs` owns the supported target-to-installer mapping and invokes Tauri in noninteractive release mode. Package, Cargo, and Tauri versions must agree. Native OS checks and rejection of Cargo target-directory overrides keep bundle discovery predictable; macOS can build either supported architecture on a macOS host. Only generated bundle output is cleared. An existing candidate directory is never overwritten, so previously recorded checksums remain reviewable.
- **Collect complete candidates separately from build intermediates.** Collection requires one nonempty installer for every expected format before creating the candidate directory. Artifact tests cover all four target mappings, byte preservation, checksum verification, missing/stale/empty installers, and refusal to overwrite. Generated packages and candidate directories remain ignored. Tauri may cache downloaded bundling utilities outside the checkout; the local AppImage build needed access to that cache after a sandbox filesystem failure. This is a build-time requirement and adds no application network permission.
- **Record provenance without treating hashes as signing.** Each candidate includes version/architecture filenames, source revision with a dirty marker when appropriate, sizes, signing status, pending acceptance, release notes, and hashes. The local Linux review candidate was built from an uncommitted tree; distribution should use a clean reviewed revision. Windows/Linux remain unsigned and macOS remains ad-hoc signed without notarization. No public release, automatic updater, or publishing step is added by packaging or by pushing source to origin.
- **Verify the packaged production AppImage without adding a production test hook.** `scripts/linux-release-smoke.py` copies the package into a temporary portable installation, launches it, replaces the file with the same candidate, and relaunches. Disposable XDG data/config/cache directories isolate the check from user data. Read-only SQLite inspection verifies schema/default-calendar/default-preference startup and restart; the helper also checks that the test-only data-directory override is ignored and port 4445 is closed. Process-group cleanup terminates the test installation. Python assertions must remain enabled. The executed path uses `--appimage-extract-and-run`, so it does not establish FUSE mounting behavior.
- **Keep evidence proportional to the executed check.** The Arch AppImage passed portable startup and same-version replacement; the deb passed metadata, executable, launcher, and icon inspection. Empty-calendar/default-preference reopening does not establish saved-event CRUD or changed-preference persistence in an installed release. Same-version replacement does not establish a version upgrade. Arch packaging does not establish Ubuntu runtime compatibility. Ubuntu, Windows/macOS installer execution, true upgrades, manual input/accessibility/high-DPI checks, and final user acceptance remain pending in the verification matrix and handoff. Windows/macOS CI entries remain disabled per the existing user decision.

Phase 5 changes packaging and verification tooling, with no event contract, SQLite schema, provider, credential, or renderer behavior changes. Exact commands, candidate paths, and observed results are recorded in `docs/handoffs/phase-5.md`.

## Shared core and standalone CLI

The Cargo workspace contains the Tauri desktop package, `aika-core`, and `aika-cli`. Contracts, SQLite migrations/validation, provider dispatch, and native credential support live in the core. The desktop re-exports its existing Rust module paths; the CLI links the core directly without Tauri or a webview dependency. Both resolve `dirs::data_dir()/dev.projectcal.desktop/calendar.sqlite3`, matching the desktop's previous Tauri convention. The CLI has an explicit database-path flag; the desktop retains its isolated native-test directory behavior.

Provider lookup is calendar-scoped and checks returned identities. Checked updates carry the original complete event; checked deletes carry that same expectation. SQLite acquires an immediate transaction before reading and comparing the stored payload, then commits the mutation atomically. Creation expects absence. Busy connections retain the existing five-second timeout; migrations also use immediate transactions to serialize first launch. Convenience Rust save/delete methods read a fresh expectation and delegate to the checked operations; desktop IPC and CLI edits use explicit expectations. No database schema change is required.

Session undo records each mutation's before and after payloads and compares the stored event with the after state inside an immediate transaction. A mismatch rejects undo without discarding history or overwriting another process's work. CLI history is process-local and inaccessible through commands; its mutations never join desktop session history. The desktop refreshes its visible range on window focus, preserving open editor drafts and their original events for comparison. See [CLI usage](cli.md) for the public command contract.

## Multiple local calendars

SQLite schema v2 adds calendar color, description, and visibility and a separate nullable default-calendar setting. Migration preserves v1 calendars, events, and application preferences. A fresh database still starts with Personal; an intentionally empty v2 database stays empty. Calendar deletion removes its events and assigns the oldest remaining calendar as default in one immediate transaction.

The desktop `calendar_snapshot` command now returns a generated `CalendarCollectionSnapshot` with all local calendars, ranged events, default identity, hidden identities, and session undo availability. Provider-level snapshots remain calendar-scoped. The registry discovers current calendar metadata for dispatch instead of retaining registration-time metadata, allowing calendars created or changed through another database connection to become available without restarting. Calendar settings updates compare original metadata; event moves compare the original complete event, verify both local calendars, update ownership and payload atomically, and reveal the destination. Undo histories referencing deleted calendars are removed, including earlier entries for the same moved events.

The renderer looks up metadata by each event's calendar ID, filters visibility before layout/counts, and uses the default only for new drafts. Calendar CRUD/default/visibility commands are serialized through the same client mutation queue as event operations. Their persistence is independent of appearance/view/sidebar preferences so automatic preference saves cannot overwrite calendar choices. The CLI creates into the current default, lists all local events independently of UI visibility, and resolves existing events by UUID without assuming Personal exists. Calendar management and event moves are desktop UI features; no remote account or sync capability is enabled.
