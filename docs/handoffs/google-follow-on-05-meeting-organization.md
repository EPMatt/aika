## Implemented behavior and architectural decisions

[Phase 05 implementation of G13](../architecture.md#phase-05-implementation-of-g13) enables organizing default Google meetings. G01–G12 retain their meaning, including the existing G07 amendment; no ADR identifiers were reassigned. Attendee data and notification choices stay outside the pure recurrence/WASM domain. Invitation responses remain phase 06.

- The native meeting-details DTO exposes organizer identity/ownership, attendee email/optional flag/response, representation completeness, existing HTTPS conference links and an opaque revision. The editor displays these details and lets organizers edit a guest list (one email per line, append ` optional`), with event details and cancellation using the established scopes. Invitees retain read-only organizer fields.
- Native meeting mutation validates the expected series and meeting revision inside the same immediate transaction as effective data and outbox writes. Guest identities are unique and checked natively; renderer-supplied responses or organizer authority cannot be written. Another connection changing only guests invalidates the review even if recurrence-domain data is unchanged.
- Every applicable write persists everyone/external-only/none (`all` by default). Google receives `sendUpdates` on insert, patch and delete, including cancellation and compensation. None requires explicit native acknowledgment of the propagation/lost-invitation warning. Ordinary existing renderer/CLI event commands preserve guests and persist the default everyone policy.
- Delivery GETs the current resource without an attendee limit, refuses omitted lists, checks the resource identity and ETag, and merges retained attendees from their current complete provider objects. Accepted/tentative/declined responses, comments, resource metadata and unknown attendee fields survive guest-list changes. New guests start at `needsAction`. Metadata-only writes omit attendees and conference data.
- Compatible recurring meetings reuse operation groups, exact compilation, real instance lookup and conditional revisions. Guest-only edits to existing exceptions explicitly retain their original occurrence selector even when the domain aggregate is unchanged. Lookup also checks the reviewed guest list before binding a new instance revision. Following edits preserve head guests and preceding exceptions; changed guests apply to the tail. Future exception reset still requires confirmation.
- Existing conferences and links remain on narrow updates. Native mutation and scope availability block following edits that would copy conferences; trim-only following cancellation remains available. Recreating a cancelled conference-bearing resource through undo is safely refused before new intent commits. Conference creation remains out of scope.

Delivered invitations cannot be recalled by undo or local discard. Stable resource identities, persisted operation markers and guest-aware achieved-state checks recover ambiguous writes before retrying, but email delivery cannot be guaranteed exactly once. This warning appears in meeting controls and guest conflict review.

## Schema/API and migration compatibility

Schema v8 adds `outbox.meeting_intent` with a persisted default all-notifications value. The transactional migration preserves existing operation/group identities, reserved resources, dependencies, attempts, acknowledgements and before/after aggregates. Pre-v8 binaries reject the upgraded database.

Generated native contracts add `MeetingGuest`, `MeetingAttendee`, `MeetingDetails`, `MeetingMutation`, `MeetingIntent` and `NotificationPolicy`; conflict snapshots include pending meeting intent and observed guests. IPC adds `meeting_details` and `mutate_meeting`. The Google transport owns notification query parameters. No credentials or meeting fields enter the pure domain, and existing CLI mutation syntax is unchanged.

## Recovery and remaining restrictions

Guest and notification intent is durable per resource step and stays overlaid while a group remains active. Retry/restart uses the persisted delivery choice. Checked conflict review includes meeting intent and observed guests; Keep local rebases unfinished resource intent and keeps guest-only occurrence scope, while Keep Google retires it and publishes observed state. Already acknowledged siblings remain effective. Unsent undo cancels the action; attempted multi-step actions still require forward reconciliation before checked compensation. Compensation preserves current response metadata and uses the original action's notification choice. Session undo history itself ends on restart.

The UI exposes existing links and email/optional-status organization; it does not create conferences, edit provider-only attendee fields, or respond to invitations. Omitted representations require complete synchronization before guest changes. Structural whole-series schedule changes, regional/DST writes, unsafe conference copying, remote moves and special event types remain restricted. Following reset compensation can restore only known cached exceptions. Disposable live acceptance and installed-platform checks remain separate from automated fixtures.

Next is Google follow-on 06: resolve the authenticated attendee natively and add participant-only accept/tentative/decline actions without granting organizer-edit capabilities. Carry forward the durable meeting/notification contracts, exact recurrence scopes, conditional revisions, checked compensation and delivery warnings.
