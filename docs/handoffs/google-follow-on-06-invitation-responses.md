## Implemented behavior and architectural decisions

[Phase 06 implementation of G13](../architecture.md#phase-06-implementation-of-g13) enables accept, tentative and decline through a separate participant-only native mutation. G01–G12, the G07 amendment and phase 05 organizer behavior retain their meaning. No recurrence-domain contracts change.

- Native identity resolution requires one non-resource, non-organizer Google `self` attendee whose email matches the verified OAuth email retained in the connected account's display metadata. The selected, active, writable calendar copy must belong to that same email. Calendar `self` alone is insufficient to authorize a delegated user's response. The renderer supplies neither attendee identity nor event fields; unknown mutation fields and unsupported response choices are rejected.
- Invitation details display pending responses and backend-approved occurrence/series scopes. The editor keeps organizer fields read-only and exposes separate Accept, Tentative and Decline buttons. Whole-series review fetches the master revision independently. Following RSVP is rejected before durable intent commits. Unsupported recurrence projections, source-zone/DST writes, special/locked/cancelled events, shared/delegated copies and unproven aliases remain restricted.
- Durable response intent includes the backend-resolved email, before/desired response, occurrence selector and a stable action identity. It reuses ordered operation groups, resource identities, per-series serialization, pending counts, lifecycle/lease fencing, conflict/discard and restart recovery. The recurrence aggregate is unchanged; meeting details overlay the pending response.
- Occurrence preflight resolves the actual instance, checks the reviewed response and binds its revision. Delivery checks the current invitation identity, authenticated attendee and ETag before patching exactly one participant with `attendeesOmitted=true` and `sendUpdates=all`. No organizer fields, other attendees, conference data, event status or private operation markers enter the PATCH. An omitted guest representation can be used if the authenticated participant remains identifiable.
- Lost responses reconcile against the observed participant effect before resending. Stale revisions produce checked conflicts displaying pending and observed responses. Keep local retains participant intent while preserving observed organizer changes; Keep Google retires it. Response-state recovery does not establish exactly-once mail delivery.
- Unattempted undo cancels the response group. Attempted responses require forward reconciliation, then checked participant-only compensation restores the previous response, including `needsAction`. Changed participant state or a superseding action from another database connection blocks undo. Stable action identity survives conflict replanning. Session undo history ends on restart; pending responses remain durable.

## Schema/API and compatibility

Schema v9 is a transactional version fence for new response intent nested in the existing `outbox.meeting_intent` JSON. It changes no tables or existing pending payloads. Earlier migrations still run in the same immediate transaction. Existing groups, operation/resource identities, dependencies, attempts, acknowledgements and notification choices survive. Older binaries reject v9 instead of interpreting a response as an empty organizer edit.

Generated native contracts add `InvitationResponse`, `InvitationResponseDetails`, `InvitationResponseMutation` and `InvitationResponseIntent`. `MeetingDetails` exposes response availability/current state; `MeetingIntent` optionally persists response intent; `SyncConflict` includes observed resource-specific participant responses. IPC adds `respond_to_invitation`. Existing CLI event mutation syntax is unchanged and does not acquire invitee organizer authority. Account identity remains the stable Google subject; the existing Google adapter supplies verified email metadata. Occurrence meeting-shadow lookup now also scopes matching remote identities by account and calendar.

## Recovery and remaining work

Responses use the existing durable synchronization and account/calendar cleanup workflows. Retry preserves participant identity, desired state, scope and notification policy. Incoming shadows remain separate from the pending response overlay. Another process changing the review invalidates it. Explicit discard retires intent without recalling an already delivered response or notification. No response action splits, creates, cancels or recreates a meeting resource.

The six-phase follow-on implementation sequence is complete. Remaining work is disposable live acceptance, installed-platform/credential-store evidence, and a separate future source-zone/DST write expansion with recurrence-equivalence evidence. Broader event types, delegated RSVP, conference creation, remote moves and exactly-once email delivery are outside this implementation.
